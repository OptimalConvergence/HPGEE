# Operations, budget and recovery

## Current end-to-end workflow

The current workflow exports inference products, not model assets. Build with `hpgee.workflows.detection.build_workflow`, prepare a result image with `prepare_exports(..., asset_id=...)`, submit through `tasks.submit_ee_export`, and refresh only the saved operation. Once the result image succeeds, fetch boundaries via `boundaries_from_raster` and actual pixels through `DownloadEngine` from that result asset. Reading this successfully materialized image no longer embeds its original classifier/features graph. Separate core exports may still evaluate training again. Direct transfer remains a measured alternative for small probes.

For multiple cores use the [bounded APIs](bounded-apis.md) to validate the cohort once and reuse its lazy RF graph. This reduces client input/graph work; it is not a server model checkpoint. For a known result image, the product resolver avoids metadata selection RPCs while retaining the shared pixel engine. Compare this transfer variant separately from an existing catalog-based benchmark; preserve the same model, source manifest, grid, bands and saved-pixel checks.

Record client submission, provider create/start/end timestamps, last-attempt batch EECU, local pixel bytes and packaging/QA separately. `batchEecuUsageSeconds` belongs to the most recent attempt; retries require attempt-aware accounting. Never add that task metric to Cloud Monitoring for the same workload tag. Completed/in-progress Monitoring views overlap; use their maximum as partial reported usage, and keep billing completeness explicit. Provider caching can make a later larger model cheaper than an earlier smaller one; one such pair does not establish a complexity ranking.

Raw `DownloadEngine` TIFF band descriptions may be absent. Preserve the raw TIFF, bind names to the frozen computePixels bandIds using `finalize_transfer`, then apply actual pixel and boundary QA. A successful task or transfer alone is insufficient.

References: [OperationMetadata](https://developers.google.com/earth-engine/reference/rest/Shared.Types/OperationMetadata), [monitoring](https://developers.google.com/earth-engine/guides/monitoring_usage), [benchmarks and cache effects](https://developers.google.com/earth-engine/guides/computation_benchmarks).

`hpgee compute manifest` (legacy `geecompute manifest`) is offline. `inspect`, `preview` and `train` perform explicit synchronous GEE work; `status` reads one exact operation. No command automatically opens a browser or submits batch exports. `usage` attempts Cloud Monitoring using explicit EE credentials, including service-account credentials if configured.

The public library `submit_ee_export` accepts prepared image/table/classifier export tasks. The journal stores intent and a REST requestId before submission. Repeating the same specification returns its recorded state; unresolved intent is SUBMISSION_UNKNOWN and requires reconciliation. `refresh_known` reads only journaled operation names. The single-journal lock serializes submissions; separate hosts need mutually exclusive shards and an agreed total budget, not multiple independent full allowances.

`max_active` is a run-local guard, not the project's actual concurrent-task limit. Read project limits and existing usage before selecting it. Budget reservations are conservatively retained for a journal's lifetime; the mechanism intentionally cannot claim provider-enforced cost caps. A real classifier export has exercised intent/submission/known-operation refresh, including FAILED and SUCCEEDED terminal states. Ambiguous transport recovery remains offline-tested; this does not establish model artifact correctness.

A calling pipeline must persist a stable unit reservation key before invoking its budget/space reservation callback. The callback must be idempotent for that key, including a crash after the hold succeeds but before its response is recorded. Keep reservation and submission intent as separate states. Unknown submission stops new tasks until the owned request/operation is reconciled; it does not release a possibly spent hold. Pipeline completion still requires the caller to verify files, coverage and hashes.

Monitoring uses a fixed caller-supplied start/end interval; a run must persist its start. A rolling 30-minute query is not cumulative usage. Completed and in-progress usage are overlapping DELTA views: report separately and use their maximum as an explicitly approximate guard, never their sum. Missing/empty/unauthorized responses are UNKNOWN. An initial bounded connectivity/source probe can precede populated telemetry; do not scale a run with unknown accounting.

Operation `batchEecuUsageSeconds` refers to the latest attempt, not necessarily all retries. A successful operation does not imply accepted files. The read-only `quota` command enumerates Service Usage limits and EE project config, checking project identity first. Limits and Monitoring usage are different resources. Noncommercial monthly quota resets at midnight America/Los_Angeles on the first day of each month, including daylight saving; use that interval before calculating a provisional balance. Delayed usage does not establish an exact remaining balance.

Keep one initialized EE project per process. The export wrapper verifies the client's actual project before submission and requires matching project/tag provenance in usage records. An immediate EECU observation is partial even when nonzero. Benchmark refresh retrieves telemetry without rerunning computation; complete cost attribution requires a recorded reconciliation before annual extrapolation.

Cloud Resource Manager and Service Usage API use is free. Reading Google Cloud's native EECU metrics does not consume EECU. Cloud Monitoring programmatic time-series reads have a billing-account-wide free allowance (as of 2026-10-13: 1 million returned series/month; excess $0.50/million), so bound polling and response cardinality. Verify current [Observability pricing](https://cloud.google.com/products/observability/pricing) when planning a long-running service. SERVICE_DISABLED requires enabling the named API; it is different from expired credentials or missing IAM permission.

An OAuth refresh error such as invalid_grant is an authentication state, not proof of an unavailable project or network. Reauthenticate interactively, keep authorization codes out of chat/logs, then repeat a bounded real request. Do not overwrite a healthy account or change its project to resolve an unrelated download issue.
